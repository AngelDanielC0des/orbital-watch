- Earth geometry: surface sphere r=1 with `surface.rotation.y = gmst`; clouds r=1.006; place outlines r=1.014; atmosphere shell r=1.045 (additive, depthTest off). Earth textures are standard equirectangular, so a GIBS equirectangular PNG maps onto a `SphereGeometry` with the same UVs.

- Precedent for an offscreen canvas texture inside the engine: `src/engine/render/track.ts` (`document.createElement("canvas")`), the only allowed `document.` use in `src/engine/**`.
- Sim time can be scrubbed ±days (`scrubDays`, `TimeTick.offsetMs`, `live` flag). Deep links are serialised from the store in `src/hooks/useUrlState.ts`.
- Deployed on Vercel (`orbital-watch-sable.vercel.app`). No env vars set. Catalog defaults to synthetic unless `?data=celestrak`.

## 1. Data architecture (Phase 2 decision)

### 1.1 Decision
**Hybrid: Next.js Route Handlers as resolver/cache + client fetch of heavy imagery from NASA's CDN + versioned static snapshots as fallback.** The Three.js engine never fetches. Data flows: Route Handler / CDN → `src/lib/layers/*.service.ts` (pure fetch + validate + normalise) → `src/hooks/useLayerData.ts` (React, owns AbortController and timers) → `src/stores/layers-store.ts` (UI state) and `EngineHandle.setLayerData(id, payload)` (engine).

| Option | Verdict | Why |
|---|---|---|
| 1. Client-side fetch direct | **yes for GIBS imagery only** | CORS `*` verified, no key, NASA CDN pays the bandwidth, the browser cache keeps repeat loads free. Not for FIRMS (no CORS, 4.5 MB) nor Open-Meteo (per-IP quota would be spent by visitors, and we need batching). |
| 2. Route Handler as proxy/cache | **yes** (`/api/orbital/ozone`, `/api/orbital/pollution`, `/api/orbital/fires`) | hides nothing secret today, but centralises date resolution, validation, binning, cache TTL and a uniform error envelope; lets us add a FIRMS MAP_KEY or OpenAQ key later without touching the client. Uses `export const revalidate = N` (ISR for GET handlers, see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md` "Revalidating Cached Data") and `fetch(url, { next: { revalidate } })`. The project does not use `cacheComponents`, so follow the "previous model" guide. |
| 3. Server Components + revalidation | no | the page is a client shell around a canvas; layer data is toggled on demand, not needed at first paint. |
| 4. Versioned static snapshot | **yes as fallback and demo** | `public/sites/orbitalwatch/data/*` already holds the OMI ozone PNG of 2026-10-29 and the colormaps; pollution and fires get a JSON snapshot generated by `scripts/snapshot-layers.mjs` (M016). Always labelled "demo / snapshot of <date>". |
| 5. Worker / background refresh | partial | no cron needed: ISR revalidation on request is enough. Client refresh timers run only while the layer is visible and the tab is visible. |
| 6. In-memory cache | yes, module-level `Map` in `geo-cache.service.ts` (client) and ISR (server). | prevents re-fetch when toggling a layer off/on inside one session. |
| 7. Filesystem cache | no | Vercel functions have an ephemeral FS; ISR is the persistent cache. |
| 8. Offline/demo fallback | yes | service chain: live → alternate live → snapshot. Status exposed as `isFallback`. |

### 4.3 Facade (additive optional members on `EngineHandle`, documented as ADR-15 in `docs/plan/PLAN.md`)
`setLayerOpacity(id, opacity)`, `setLayerData(id, payload)`, `clearLayerData(id)`. `toggleLayer` already exists. `removeLayer` is not added: layers are created at boot and hidden, never removed (StrictMode-safe, matches T17 pitfalls). `refreshLayer` is UI-side (hook), not an engine command. Implementation in `create-engine.ts` is 3 one-liners delegating to `LayerManager` (`getDataLayer(id)` guards `"setData" in layer`). The engine registers `ozone`, `pollution`, `fires` from `DEFAULT_LAYERS` with `visible: false`; the hook pushes data only when visible, so a hidden layer costs one empty `Group`.

### 4.4 Three.js integration rules
- Textures from `ImageBitmap`: `new Texture(bitmap)`, `flipY = false` with `imageOrientation: "flipY"` on `createImageBitmap`, `colorSpace = SRGBColorSpace`, `minFilter = LinearFilter` (no mipmaps for 2:1 non-power-of-two on `lo`; GIBS 2048×1024 is power-of-two so mipmaps are allowed), `anisotropy` from renderer. Call `renderer.initTexture` then `bitmap.close()` as `Earth.applyTextures` does. Dispose the previous texture after swapping.
- `DataTexture` for heatmap: `RGFormat`, `UnsignedByteType` normalised (count log-scaled to 0–255 server-side to avoid float textures on `lo`), `needsUpdate` once per payload.
- Materials: `transparent: true`, `depthWrite: false`, `depthTest: true`, `renderOrder` 2 (raster) / 3 (points) so they draw after clouds (1) and before the hover ring. Polygon offset is unnecessary because radii differ (1.009 / 1.0095 / 1.011).
- Rotation: `object3d.rotation.y = ctx.gmstRad` every frame (same as `Earth.update`). No per-frame allocations; uniforms mutated in place.
- Visibility: `setVisible(false)` hides `object3d`; `LayerManager.update` already skips invisible layers.
- Disposal: each layer `dispose()` is idempotent and frees geometry, material, LUT, current texture; `ImageBitmap.close()` on the client cache when evicted; `AbortController.abort()` in hook cleanup; timers cleared; the engine `dispose()` already calls `layers.dispose()`.
- No `fetch`, `window.location`, React or store imports in `src/engine/**` (lint-enforced).

### 4.5 Performance budget
| Item | Budget |
|---|---|
| Added draw calls with all three layers on | ≤ 4 |
| GPU memory | ozone 2048×1024 RGBA ≈ 8 MB (+mips 11 MB) on `lo`, 4096² ≈ 45 MB on `hi` only; heatmap 720×360 RG ≈ 0.5 MB; LUTs negligible |
| Points | pollution ≈ 430; fire hotspots ≤ 2 000 (`hi`) / 800 (`lo`) |
| Network per session (all layers once) | ozone ≈ 1 KB JSON + 135–430 KB PNG; pollution ≈ 40 KB gzip; fires ≈ 150–300 KB gzip |
| Server | Open-Meteo ≤ 4 upstream calls per hour (430 coords / 150 per batch); FIRMS 2 CSV downloads per hour per window (≈9 MB); GIBS 2 tiny requests per 6 h |
| React | zero re-renders at frame rate (layers-store is written only by hooks on status changes); opacity slider writes the engine directly on `input` and the store on `change` (debounced 150 ms) |
| Mobile | `lo` tier: 2048 textures, 800 hotspots, no pulse animation |

### 4.6 Security
- No secrets today. If `FIRMS_MAP_KEY` or `OPENAQ_API_KEY` are ever added they are read only in `src/lib/server/**` from `process.env` (never `NEXT_PUBLIC_`), documented in `.env.example` as optional.
- Route Handlers validate every query param against allow-lists (`window`, `layer`, `date` regex `^\d{4}-\d{2}-\d{2}$`), never forward user input into upstream URLs unvalidated, cap response sizes (abort FIRMS stream > 40 MB), set `Cache-Control: public, s-maxage=…, stale-while-revalidate=…`, return JSON only.
- Client services validate upstream shapes with the tiny guards in `validate.ts` (no new dependency): reject NaN/out-of-range values, cap arrays, treat unexpected columns as errors.
- Images are only loaded from `gibs.earthdata.nasa.gov` or `/sites/orbitalwatch/data/` (allow-list in `ozone.service.ts`).

## 5. Timeline interplay (explicit)
The existing timeline scrubs simulated time ±days. Environmental layers are *observational snapshots*; in MVP they do not change with sim time. The UI states it plainly ("Datos del 29 oct · no siguen la línea temporal") and the ozone service is designed with an optional `date` so phase 2 can bind it to `TimeTick` (GIBS archive to 2004) with a 1-day debounce and the same cache keyed by date.

## 6. Open questions for the user (do not block; defaults stated)
1. Commercial status of the site (donations exist): Open-Meteo is free for non-commercial use; ads or subscriptions would require their paid plan. Default: assume non-commercial.
2. Should environmental layers be reachable from `?layers=` deep links at launch? Default: yes (cheap, M011).
3. Prefer OMI (4-day latency, long archive) or wait for a NOAA-21 OMPS layer in GIBS? Default: OMI now, candidate chain ready.
4. Spanish-only UI stays? Default: yes (matches the HUD).
